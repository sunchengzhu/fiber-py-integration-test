# Gate1：Hosted 通道的开通限制与延迟签名

本文件保留为候选范围。综合 `0f41d9a → 4028884` 的近期提交后，建议优先评审 SSE 签名通知的租户隔离、待签补发与会话接管；本候选不再作为已选定的下一批，尚未进入 Gate2。

这批回答两个实际问题：**别人能否绕过用户同意，反向给 Hosted 租户开通道？用户一时没签名，原支付还能否保留并恢复，其他租户是否受影响？**

沿用本对话的阶段：Gate1 确认范围和环境能力，Gate2 展开带稳定 ID 的中文用例表，Gate3 在用例表明确通过后实现 Python 测试。本轮只提交范围，不新增 TEST-MAP，不运行新增场景。

## 为什么现在补

产品基线为 `40288844157cac8dd7fb025304be276cb1ac1f0b`；FNN、SDK agent 和本地 SDK 驱动已统一到该版本。
测试仓库为基于 `v0.10.0 / 6088115` 的 `codex/lsp-core-regressions`。已有 16 条在本版本全部通过，见 [运行说明](../../test_cases/fiber/devnet/lsp/README.md)。

本轮重点来自该版本新增的 `408beaa`：

- Hosted 租户不接受别人发起的通道；租户主动开通仍须使用用户自己的外部签名材料。
- 公共 LSP 对已注册租户的内部通道，不再按普通 ACK／重连活动超时直接强关；TLC 的资金安全截止仍有效。
- 这项等待保护不应依赖客户端一直在线、持续查询签名状态或探测签名端。

已有测试有短暂断线、HTTP 超时及进程恢复，但没有明确把“付款已到达租户、公共 LSP 等 ACK、暂停超过 30 秒”作为必须到达的检查点；偶然运行较慢不能算覆盖了这条边界。
已有租户隔离验证的是开通期间互不阻塞，尚未证明一个租户收款等签时，另一个租户的付款能完成。

## 建议本批覆盖的四个方向

以下是范围候选，不是已经批准的用例行。Gate2 再分配 ID、确定参数和每一步断言。

| 方向 | 如何构造场景 | 必须看到的结果 |
| --- | --- | --- |
| 反向开通被拒绝，且不伤害正常通道 | 公共 LSP T 向 Hosted 租户 A 发起开通；分别覆盖 A 尚无通道、A 已有自己主动开通的可用通道 | 发起侧明确进入开通失败，不能一直挂着；A 不新增通道或待接受请求，不产生新注资输出；已有通道仍可完成一笔真实收款 |
| 用户延迟签名，原付款继续 | P 经 T 向 A 付款；在 A 的目标支付签名尚未提交、T 等待 ACK 时暂停至少 35 秒，然后恢复 | 等待期间原通道和待签请求保留，没有提前强关；恢复后原 payment hash 成功、发票已支付、TLC 和锁定额清空，余额只结算一次 |
| 客户端完全离线也能等待 | 到达同一支付检查点后停止 A 的 SDK，确认事件连接关闭；至少 35 秒内不向 A 查询或提交签名，再用原存储和授权启动 | 无客户端查询也不提前强关；恢复同一请求和原支付，不重新授权或重发付款，最终金额及费用正确 |
| A 等签不妨碍 B 收款 | A、B 通道均已就绪，暂停 A 的支付签名超过 30 秒；期间向 B 发起独立付款并正常签名，最后放行 A | B 在 A 仍暂停时完成自己的付款；A 此时不能被算作已支付，恢复后也完成；两笔 payment hash、发票、通道余额和费用分别对应，不串单或重复结算 |

第一项的“RPC 返回成功”不等于通道开通成功：T 可能先返回临时通道 ID，再收到 A 的拒绝。必须追踪该 ID 的失败结果。
查询 `list_channels(only_pending=true)` 时，只将 `Closed + FUNDING_ABORTED` 识别为失败；不能把普通待开条目当成失败记录。

## 时间控制和避免假通过

- 本次运行的 FNN 是普通 dev 构建，未启用 `bench`。源码普通 ACK 等待阈值为 **30 秒**；Rust 单元测试编译条件下是 10 秒，不能把后者照搬到 Python 集成测试。
- **35 秒 = 30 秒阈值 + 5 秒观察余量**，用于明确跨过这条边界，不是新的产品 SLA。起点必须晚于目标 TLC 到达及目标待签请求建立；不能从开始创建节点或发起付款时计时。
- 优先选 A 的 `CompleteReceivedCommitment` 待签检查点，并核对目标 payment hash。结合 T 的 ACK 状态日志确认确实发生了等待；具体可观察字段和日志关联方法在 Gate2 固定。无法证明检查点就算准备失败，不改成任意暂停点。
- 等待期间可以查询公共 T 的通道和付款状态，但“完全离线”方向不得向租户 A 的运行时发起查询，以免查询本身改变被测条件。必须确认 SDK 进程和已有 SSE 连接都已结束；仅打开 `pause_queries` 不足以证明旧事件连接已断。
- 使用真实 `send_payment`，沿用现有发票和 SDK 授权，不用 `dev_add_tlc`。实际 TLC 截止及授权有效期在暂停前须至少剩余 900 秒，放行前仍至少剩余 180 秒；不混入业务到期强关。
- 在线暂停时持续检查“不提前关闭、请求未被应用”；离线时由公共侧状态及节点日志辅助观察，恢复前后比较原请求。事件满足立即推进，不靠固定睡眠后只查一次终态。
- 恢复沿用现有有界等待与资金断言：原支付成功、发票 Paid、pending TLC 和锁定额归零、四端余额及实际路由费一致，并检查稳定期内没有二次变化。没有重新发送付款的兜底。
- A、B 共用付款节点时，必须分别保存每笔支付前后的余额检查点，按各自金额和费用计算；不能把共享节点总余额变化全部归给其中一个租户。

## 已有能力与需要在 Gate2 落实的部分

| 能力 | 当前情况 |
| --- | --- |
| 同版本 FNN/SDK、独立 devnet 环境、租户身份及通道 | 已有，原 16 条通过；每条新用例继续使用独立 Fiber 状态 |
| 真实付款、签名拦截、SDK 终止及原存储恢复、余额核对 | 已有，可复用 LSP 辅助代码；不需要修改公共框架或产品实现 |
| A 没有任何通道时接收反向开通 | 现有夹具会自动开始租户开通；需要局部提供“只注册、不自动开通”的准备方式，Gate2 写清最小改动 |
| T 的 ACK 等待检查点 | 上游测试能读内部状态；Python 需落实目标通道日志与待签请求的对应关系，不能宣称直接复用内部测试钩子 |
| 两租户分别收款 | 现有隔离夹具支持两租户，收款辅助方法目前按单租户保存状态；需要局部保存两笔付款的独立上下文，避免共享变量覆盖 |
| 强关最终结算 | 本批不需要；仍是独立的 watchtower 缺口，不用“未强关”代替最终资金取回验证 |

Gate3 若无法达到已确认的检查点，返回评审调整前提，不修改产品代码、不降低预期。此处的可复用能力不等于四个新方向已经执行通过。
